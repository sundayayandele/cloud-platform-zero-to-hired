- Do the same on **Google Cloud** with the `google` provider, and compare the three clouds.

## Why this matters at work

State is the most fragile part of Terraform. Two engineers applying at the same time with local state files can each overwrite the other's changes, or both create the same resource. A lost state file means Terraform no longer knows it manages production, and the next apply tries to build everything again. A state file in a public repository can leak database passwords. Every team using Terraform has rules about state; you'll be expected to set it up correctly on day one and never be the person who breaks it.

## 1. What state is

After every apply, Terraform records in **state** (a JSON document):

- each resource address in your code (`module.network.aws_subnet.app[0]`) and the real ID it maps to (`subnet-0a1b2c...`);
- every attribute Terraform knows about it, including generated values;
- dependencies, outputs and the provider used.

On the next plan, Terraform **refreshes** state from the cloud APIs, compares it with your code, and plans the difference. Without state, it can't tell "the subnet I created" from "a subnet someone else created".

State commonly contains **secrets**: database passwords generated by Terraform, keys, connection strings. Treat the state file like a password file.

## 2. Remote state with locking

A local `terraform.tfstate` is fine for a lab, never for a team. A **remote backend** stores state in shared, durable storage, and **locks** it during plan and apply so only one person (or pipeline) changes it at a time.

**AWS: an S3 bucket**

Create the bucket once, by hand or with a separate small configuration (you can't store the state of the bucket that holds the state in itself):

```bash
aws s3api create-bucket --bucket itlpay-tfstate-ada --region af-south-1 \
  --create-bucket-configuration LocationConstraint=af-south-1
aws s3api put-bucket-versioning --bucket itlpay-tfstate-ada --versioning-configuration Status=Enabled
aws s3api put-public-access-block --bucket itlpay-tfstate-ada --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

Then in the configuration:

```hcl
terraform {
  backend "s3" {
    bucket       = "itlpay-tfstate-ada"
    key          = "dev-aws/network.tfstate"
    region       = "af-south-1"
    encrypt      = true
    use_lockfile = true      # S3-native locking (Terraform 1.10+); older setups used a DynamoDB table
  }
}
```

**Azure: a storage account**

```bash
az group create -n rg-tfstate -l southafricanorth
az storage account create -n tfstateada -g rg-tfstate -l southafricanorth --sku Standard_ZRS \
  --allow-blob-public-access false --min-tls-version TLS1_2 --allow-shared-key-access false
az storage container create --account-name tfstateada -n tfstate --auth-mode login
az role assignment create --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --role "Storage Blob Data Contributor" --scope "$(az storage account show -n tfstateada --query id -o tsv)"
```

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "tfstateada"
    container_name       = "tfstate"
    key                  = "dev-azure/network.tfstate"
    use_azuread_auth     = true   # Entra ID instead of storage account keys
  }
}
```

The azurerm backend locks with a **blob lease**, automatically.

**Google Cloud: a Cloud Storage bucket**

```bash
gcloud storage buckets create gs://itlpay-tfstate-ada --location=africa-south1 \
  --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://itlpay-tfstate-ada --versioning
```

```hcl
terraform {
  backend "gcs" {
    bucket = "itlpay-tfstate-ada"
    prefix = "dev-gcp/network"
  }
}
```

The `gcs` backend locks automatically (it writes a lock object next to the state), and uses your Application Default Credentials. Turn on blob **versioning** and **soft delete** on the storage account so a damaged state can be restored.

After adding a backend block, run `terraform init` again. If local state exists, Terraform offers to **migrate** it to the backend: say yes, check `terraform state list` shows everything, then delete the local file.

If an apply is interrupted, a lock can be left behind. `terraform force-unlock LOCK_ID` removes it, but **only** after you're sure nobody else is running: otherwise you've removed the safety catch while someone is mid-apply.

## 3. Protecting state

| Protection | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Private | Block Public Access | Public blob access off; consider a private endpoint | Public access prevention; uniform bucket-level access |
| Encrypted at rest | `encrypt = true` (SSE); a KMS key for stricter control | Encrypted by default; customer-managed keys if required | Encrypted by default; Cloud KMS keys if required |
| Recover from mistakes | Bucket versioning | Blob versioning and soft delete | Object versioning and soft delete |
| Who can read it | IAM: only the people and pipelines that run Terraform for that environment | RBAC: *Storage Blob Data Contributor/Reader* on the container, for the same people | IAM: *Storage Object Admin/Viewer* on the bucket, for the same people |
| Separate production | A separate state bucket in the production account | A separate storage account in the production subscription | A separate state bucket in the production project |

Anyone who can read production state can read whatever secrets are in it, so production state access should be as tight as production itself.

Better still, keep secrets **out** of state: let the platform generate and hold them (RDS `manage_master_user_password`, topic 6.7; Key Vault references), so Terraform only ever handles the secret's name or ARN.

## 4. Environments: one state each

Dev, staging and production must have **separate states**, so a mistake in dev can't touch production. Two ways:

- **Separate folders** (`envs/dev-aws`, `envs/prod-aws`), each with its own backend `key` (and, for production, its own bucket or storage account and account or subscription). Each folder calls the same modules with different inputs.
- **Workspaces** (`terraform workspace new staging`): one folder, several states. Convenient for short-lived copies (a test environment per pull request), but every environment shares the same code and backend settings, and it's easy to apply in the wrong workspace.

Most teams use **folders per environment** for long-lived environments, because the differences are visible in the code and in reviews, and production can use different credentials and a different backend. This course does the same. Tools such as Terragrunt reduce the repetition between environment folders; you'll meet them at some companies.

## 5. Inspecting state safely

```bash
terraform state list                                   # every resource address
terraform state show 'module.network.aws_vpc.this'     # one resource's attributes
terraform output                                       # outputs
terraform show                                         # the whole state, readable
terraform state pull > backup.tfstate                  # a copy, before anything risky (store it safely, delete after)
```

Commands that **change** state (`state mv`, `state rm`, `import`) are covered in topic 7.5, together with the safer code-based alternatives (`moved`, `removed` and `import` blocks). Never edit the JSON by hand.

## 6. Sharing values between configurations

The network and the application are often separate configurations (owned by different teams, applied at different times). The application needs the network's subnet IDs. Options, from most to least coupled:

1. **`terraform_remote_state`** data source: reads another configuration's outputs straight from its state. Simple, but needs read access to that whole state (including any secrets in it).
2. **Data sources by tag or name**: `data "aws_subnets" "app" { filter { name = "tag:tier" values = ["app"] } }`. No access to the other state needed, and it works even if the network was built another way.
3. **A parameter store**: the network configuration writes its outputs to SSM Parameter Store or Azure App Configuration; others read them. Clear contract, narrow permissions.

Prefer 2 or 3 between teams; 1 is fine within one team's configurations.

2. Add the backend blocks to `envs/dev-aws`, `envs/dev-azure` and `envs/dev-gcp` from the network lab, run `terraform init`, migrate the state, and confirm with `terraform state list`. Check you can see the state objects in S3, Blob Storage and Cloud Storage.
3. Prove locking works: start `terraform apply` in one terminal and, before confirming, run `terraform plan` in another. Read the lock error.
